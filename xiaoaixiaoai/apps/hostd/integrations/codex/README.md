# Existing Codex sessions

This connector is **not** a way to take over the Windows Store Codex desktop app. It attaches only to an explicitly provisioned, trusted App Server that already owns the selected thread in memory. An installed MSIX and running Desktop processes do not prove that such an endpoint exists. No live Desktop endpoint or actual chat was inspected or used by this implementation.

## Operator prerequisites

- Provision the connector on the same host/loopback as the **already running server that owns the intended threads**. The endpoint must be `ws://127.0.0.1:<port>` (an optional trailing slash is allowed), with WebSocket authentication enabled. Hostnames, IP aliases, redirects, proxies, private pipes, and background discovery are not supported.
- The [App Server transport docs](https://learn.chatgpt.com/docs/app-server.md) describe `--listen ws://127.0.0.1:<port>` and `--ws-auth capability-token --ws-token-file <absolute-token-file>`. WebSocket transport is **experimental and unsupported** by Codex. Use a private, high-entropy capability token, not a ChatGPT or relay token. Provide it to hostd through its private token-file configuration, not in the URL, shell arguments as a raw value, or shared logs. With this exact trusted URL, the connector requires an anonymous upgrade to fail before sending the configured `Authorization: Bearer` credential. This detects a normally unauthenticated listener; it does not independently authenticate the server process.
- The [official daemon docs](https://github.com/openai/codex/blob/main/codex-rs/app-server-daemon/README.md) describe a **managed daemon** and its Unix/AF_UNIX control socket (including on supported Windows builds). They do not document attaching this WebSocket to the currently running standalone MSIX Desktop backend. Bootstrap, starting a separate `codex app-server`, or loading the same saved history in a new process is **not** evidence of same-server ownership. The connector does not launch, reconfigure, or restart Codex, look in `CODEX_HOME`, or guess a Desktop-only transport. If you cannot establish this prerequisite for Desktop, leave the connector disabled.
- Allowlist exact thread ID / local project ID pairs. Read access alone does not enable sends. In hostd, writes require both the operator's `exclusiveWriter` assertion and `canSend: true` for that exact thread. Use this only where you can prevent all concurrent input to that thread from Desktop, scripts, queues, or other clients. Otherwise keep it read-only. The [upstream `turn/start` implementation](https://github.com/openai/codex/blob/main/codex-rs/app-server/src/request_processors/turn_processor.rs) can steer if another turn starts before input is admitted; the public request has no atomic idle precondition. Client-side freshness checks narrow, but cannot close, that race.

## Status and receipts

Each operation initializes a new authenticated connection, then uses `thread/loaded/list` and exact `thread/read {threadId, includeTurns:false}` on that same connection. The catalog exposes only allowlisted IDs, bounded names, and status—not the thread preview, history, paths, or other loaded IDs. A consistent `"idle"` snapshot is eligible only with the write grant. `"active"` displays as `running`, or `attention` if it is waiting on approval or input. `"systemError"` maps to `attention`; a confirmed `"notLoaded"` maps to `inactive`. Contradictory, missing, or unrecognized state is not writable. Sending rechecks rather than trusting the catalog.

The only mutation is a single `turn/start` with the exact thread ID and one text input. The connector never creates, resumes, steers, interrupts, adds attachments/tool outputs, changes settings, or answers server requests. Use the authorized native client for any approvals. No prompt or raw server payload is logged or stored by this adapter.

A matching `turn/start` response containing a valid `turn.id` with status `"inProgress"` proves **acceptance**, not completion. If the connection drops, times out, or returns an unverifiable acknowledgement after dispatch, `turn_acceptance_unknown` means the original thread must be checked. Do not automatically resend. The in-memory connector fences further sends to that thread until it is explicitly re-enabled or restarted after inspection. A verified rejection such as WebSocket ingress overload or a detected pre-dispatch failure is not an acceptance.

## Verification

`cd apps/hostd && node --test test/codex-runtime.test.ts` uses an ephemeral authenticated IPv4 loopback fixture only. It does not use any live Codex endpoint, real chats, or Desktop state.
